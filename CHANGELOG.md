# Changelog

## v0.6.0

**Native Snell (Surge) protocol.** Snell v5 and v6 (beta) are created and managed by Rout itself, next to VLESS Reality, AnyTLS, Shadowsocks 2022, Hysteria2 and TUIC. Nothing else has to be installed; existing nodes, relays, exits, AI routing, subscriptions, tokens, traffic data and the web panel are unchanged (the existing test suite passes as before; the one test that iterates every create-menu protocol now also checks Snell's configuration). Full guide: [docs/SNELL.md](docs/SNELL.md).

- **Creation and lifecycle.** *Quick create node* offers **Snell v5** (6) and **Snell v6 (beta)** (7): random 32-character PSK, free or chosen port, IPv4 or dual-stack listening, NAT-aware public port, custom PSK under *Advanced options*, node name `Base-Snell` / `Base-Snell6`. Edit port / public address, **listen address** (new, Snell nodes), **PSK** (new), rename, outbound IP family, start/stop/restart, logs, delete, traffic and quota work like for every node. Several Snell nodes (any mix of v5 and v6) are isolated by stable ID: own service `rout-<id>`, own `snell-server.conf` (mode 0600), own nftables table, own port.
- **Official engines, verified.** `snell-v5` (Snell server 5.0.1) and `snell-v6` (6.0.0) are pinned by SHA-256 in `engines.lock.json` and downloaded only from `dl.nssurge.com` for amd64 and arm64. The installer now also reads `.zip` archives (member matched by base name, size and CRC checked, never written outside staging) and knows glibc-only builds: **v6 is glibc-only and is refused on Alpine/musl with an explicit message** (v5 is static and works there); platforms without an official build are refused, never substituted. Install is atomic, locked and leaves the previous engine untouched on any failure; engines of other protocols are not touched.
- **Surge configuration.** Creation, *Manage nodes*, `rout copy|export ID`, `rout export all` and the panel's share-link dialog show `Name = snell, host, port, psk=…, version=N` (public address and port, IPv6 without brackets, names made safe). `version` is always explicit. The panel's `GET /api/nodes/{id}/link` returns it with `"format": "surge"` (re-authentication required, as for every link).
- **Subscriptions.** Snell nodes can join subscriptions; new `?format=surge` returns their Surge lines (live: edits, renames, disable and delete are reflected on the next fetch). Base64 and Mihomo/Clash output are unchanged and skip Snell with a diagnostic; nothing is converted into another protocol.
- **Traffic.** Same kernel accounting and hard quotas; v5 also meters UDP on its port (QUIC Proxy Mode) and reserves it against other protocols.
- **Honest limits.** No outbound proxy / exit (rejected, skipped with a warning in batch flows), no AI Smart Routing (listed as not eligible), no sing-box client file, no Mihomo export, no "IPv6 only" listener on a dual-stack host (the engine cannot do it), no claim that an outbound IP family is *enforced* for Snell. `rout test` states that the Snell handshake can only be verified in Surge. Snell PSKs are redacted from every log Rout displays.
- **Languages.** All new text exists in 简体中文, English and 繁體中文.
- **Tests.** 33 new test functions (plus table cases and subtests): configuration for every variant (only documented keys), PSK rules, version/engine selection, Surge syntax, multi-instance lifecycle and isolation, port conflicts (TCP/UDP), NAT, systemd/OpenRC definitions, nftables rules, refusals, subscriptions, create/edit flows, web API, state round trip, engine install and hostile-archive tests, plus a **CI test that runs the real official engines** on Rout's configuration (Linux, `ROUT_TEST_ENGINES`). A test that a lying zip is rejected found and fixed an unchecked CRC in the new extractor.
- **Not verified here:** a real VPS / NAT VPS / arm64 host with real systemd, and Surge iOS connecting (see [Verification status](docs/SNELL.md#verification-status) and the Surge iOS acceptance checklist).

## v0.5.2

**Node outbound IP family.** Each node can choose how it reaches the Internet: **Auto** (default, exactly the previous behaviour), **IPv4 first**, **IPv6 first**, **IPv4 only** or **IPv6 only**. Details, the sing-box findings and the limits: [docs/NODE_EGRESS.md](docs/NODE_EGRESS.md).

- **A real "only", not a DNS preference.** With the pinned sing-box 1.14.3, `domain_resolver.strategy = ipv6_only` fails A-only *names* but does **not** stop a client that asks for an IPv4 *address* (checked with the real engine). Rout therefore also writes a route rule (`ip_version` → reject) on a Direct node, which refuses IPv4 literals and IPv4-mapped IPv6 literals under IPv6 only (the mirror for IPv4 only). IPv6 first / IPv4 first are preferences with fallback and are not IPv6 only / IPv4 only. The removed `domain_strategy` is never generated.
- **Terminal:** *Create node → Advanced options → Outbound IP family* (fixed numbers 1–5, default Auto; quick create asks nothing) and *Manage nodes → choose a node → Outbound IP family* (new last entry, earlier numbers unchanged: change the policy, *Test IPv6 egress*, *Show outbound IPs*). The node card shows the policy for non-Auto nodes. A family the host has no route for is annotated and needs explicit confirmation for an "only" policy.
- **Web panel:** the same selector in *New nodes* and in the node drawer (current value, enforced or not, *Save policy*, egress test), mobile friendly, zh-CN / zh-TW / en. API: `outbound_policies` and per-node `outbound_policy` / `outbound_scope` / `outbound_enforced` in `GET /api/nodes`, `outbound_policy` / `force` in `POST /api/nodes`, `PUT /api/nodes/{id}/outbound-policy` (`409 no_route` until confirmed), `POST /api/nodes/{id}/egress-test`.
- **One code path.** Menu and panel both call `SetNodeOutboundPolicy`: validated (including `sing-box check`), only that node rewritten and restarted, previous files and state restored on failure; UUID, port, certificate and subscription links untouched.
- **Outbound proxies** (SOCKS5, HTTP/HTTPS CONNECT, remote node): the policy governs only the connection to the proxy server; the website-side family is the proxy's decision and is reported as *not enforced*, never claimed. A literal proxy address of a forbidden family is refused when saving; nothing falls back to Direct.
- **Egress test** (`POST /api/nodes/{id}/egress-test`, menu): real requests through the node's own inbound, controls from the host (labelled *Host network test*), a request to a bare address of each family, and verdicts `pass` / `fail` / `inconclusive` — an unprovable exclusion is never shown as a pass; a node that leaks is reported as failing. The layered diagnosis names the policy of the node.
- **Compatibility:** Auto is stored as unset and renders a configuration identical to v0.5.1's (75 configurations — 5 protocols × plain / IPv6 inbound / three proxy kinds × plain / AI routing / AI fail-closed — compared against the base commit's output); `state.json` of such nodes gets no new key. Backups, restores, `rout apply`, restarts, relays (own `outbound_policy`), NAT-VPS hosts and AI routing are unaffected. Downgrading to v0.5.1 loads the state but does not apply node policies (see [Upgrading](docs/UPGRADING.md)).
- **Verification status.** Automated: configuration shape and legacy parity, **real sing-box** matrix (IPv6/IPv4 only, IPv6/IPv4 first, Auto; A-only, AAAA-only, dual-stack names; IPv4, IPv6 and IPv4-mapped literals; DNS failure; origin-side connection counters proving no fallback; the resolver-alone question; proxy exits; a real VLESS Reality client; policy switching and `apply`; the egress test against a leaking node), menus and API tests, English/zh-TW catalog coverage, panel component tests. Each enforcement test was mutation-checked (removing the rule, downgrading `ipv6_only` to `prefer_ipv6`, dropping the resolver all fail it). **Not done:** a real dual-stack VPS (the Turkey/VLESS acceptance scenario in [docs/NODE_EGRESS.md](docs/NODE_EGRESS.md#7-limits-and-what-was-not-verified)), real providers and phones. The development sandbox has no IPv6, so IPv6-success paths run in CI only.

## v0.4.0

Architecture-level feature release: independent IPv4/IPv6 control, a native TCP/UDP relay engine, Remote server exits and layered diagnostics. Existing nodes, relays, exits, subscriptions and settings keep working without migration. **Real VPS/NAT acceptance has not been done for this release; see "Verification status" at the end of this section before deploying it to a production host.**

- Highlights: inbound IPv4 / IPv6 / dual stack chosen per relay; outbound IPv4 first / IPv6 first / IPv4 only / IPv6 only / auto; IPv6 → IPv4 and IPv4 → IPv6 forwarding; Rout's own TCP/UDP relay engine; Remote server exits (node share link, SOCKS5, HTTP/HTTPS); Hysteria2/TUIC UDP capability detection that refuses incompatible relays; layered diagnostics with a real-exit test; stale-DNS and UDP-diagnostic fixes.
- **Independent inbound and outbound address families.** A new relay asks which family clients reach it on — **IPv4 (default)**, **IPv6** or **dual stack** — offering only what the host can really bind, and (on a host that can route both families) how it reaches its destination — **IPv4 first**, **IPv6 first**, **IPv4 only**, **IPv6 only** or **auto**. The two are independent, so IPv6 → IPv4, IPv4 → IPv6 and dual stack → either family are ordinary TCP/UDP forwarding with no NAT64. The saved server-wide `::` default no longer decides how a relay listens: a dual-stack host could not choose IPv4-only, and the node menu's "IPv6" choice silently produced a dual-stack listener. An explicit IPv6 node now refuses IPv4 clients (the first routing rule rejects `0.0.0.0/0`, because sing-box cannot set `IPV6_V6ONLY`), is metered for IPv6 only and prints no IPv4 link.
- **Native relay forwarder.** New relays run on Rout's own forwarder (`rout relay-serve`, hidden command, started from a copy of the manager next to the engines, same sandboxed unit with no extra capabilities). One explicit `tcp4`/`tcp6`/`udp4`/`udp6` socket per family (`IPV6_V6ONLY` on every IPv6 socket; dual stack is two sockets, verified to be able to share a port); outbound policy applied per connection; domain destinations re-resolved when their 30 s cache entry expires or when every cached address fails (a brief DNS outage reuses the last answer for ≤10 minutes and says so); TCP half-close, UDP sessions with idle expiry, connection and session limits, refusal to dial its own listener, prompt stop with live tunnels. It forwards bytes only: no credentials, no proxy protocol, no listener beyond the relay's own ports. **Relays created by earlier versions keep running on GOST with a byte-identical configuration**; *Edit relay → Change network* moves one after a preview (same port, destination and share link). Renaming or disabling a legacy relay does not migrate it.
- **Remote server exits.** Outbound proxies gain a *Remote server* kind: another VPS/NAT whose public IP the traffic leaves from, reached through a remote node's share link (VLESS Reality, AnyTLS, Trojan, Shadowsocks, Hysteria2, TUIC — the existing sing-box outbound, no new proxy core) or an authenticated SOCKS5/HTTP(S) proxy. A bare port mapping is refused as "port forwarding, not an exit". A Remote server is verified with a real request before it is saved (answering *Save anyway* is explicit), Hysteria2/TUIC over a TCP-only NAT is refused, certificate-pinned Hysteria2 links are refused, and nothing opens a listener on this server. Exits are stored once and reused: nodes pick them by number (a *New outbound proxy* entry creates one on the spot), editing one changes only the nodes that reference it, deleting a referenced exit is refused with the node names, and *View* lists the references (nodes and AI Smart Routing) without credentials. Exits pointing back at this server are refused as routing loops. Exits written by earlier versions load unchanged and serialize without the new fields.
- **TCP/UDP capability model.** Links settle the transport (VLESS/AnyTLS/Trojan: TCP; Hysteria2/TUIC: UDP; Shadowsocks: either); a relay for a QUIC protocol aimed at a TCP-only destination — declared by the user, or a TCP relay for a Hysteria2/TUIC link — is refused with an explicit message instead of writing UDP into a TCP socket. UDP-over-TCP encapsulation was evaluated and not implemented (it needs a decapsulating peer on the far side, adds head-of-line blocking and cannot be made transparent to QUIC); see [docs/NETWORK.md](docs/NETWORK.md).
- **Layered diagnostics** for `rout test ID`, *Test relay* and *Test outbound proxy*: local sockets per family (read from the kernel), destination resolution against the policy, a real TCP handshake or a QUIC Version Negotiation probe, a connection through the relay's own entry (a relay that accepts and drops is no longer "listening ✓"), TLS camouflage / SOCKS5 / HTTP credential handshakes, and the real exit per family. The catch-all "request failed (connection, authentication, TLS or network unavailable)" is replaced by the actual stage and cause (DNS, refused, timeout, no route, TLS, authentication, proxy chain). A reachable TCP port is reported as `! The proxy protocol handshake has not been verified`, never as a working node.
- **CLI.** Relay creation: recognized link line (`Recognized: TCP / VLESS Reality`), transport taken from the link, inbound network, outbound policy, name, confirmation; the choices are remembered as defaults. Relay cards and `rout doctor` show each relay's inbound and outbound settings. Existing menu numbers are unchanged (*View outbound proxy* is the last entry; *New outbound proxy* follows Direct in the picker).
- Compatibility: new profile fields (`inbound_mode`, `outbound_policy`, `engine`, `target_network`) and exit fields (`kind`, `remote_network`, `link`) are omitted when empty; nothing is migrated automatically, share links and subscriptions are byte-identical for legacy and native relays. Older Rout cannot read Remote server exits; see [Upgrading](docs/UPGRADING.md). Developers: `Proxy` now has a `Link` field, so positional struct literals need field names.
- Tests: unit and simulated tests (family model, policies with injected DNS/dialers, dynamic domains, stale DNS, capability refusals, exits, migration, scripted bilingual UI, layered diagnosis on real loopback sockets and a QUIC responder), engine integration tests (all five protocols through the native forwarder, remote-node exit with right and wrong credentials, IPv6-only node refusing IPv4 clients, `rout relay-serve` as a real process, the hardened systemd unit), and opt-in real-network tests (`ROUT_TEST_REALNET=1`). IPv6 socket tests skip on hosts without IPv6. Loopback tests are not VPS/NAT acceptance: real provider NAT, firewalls and IPv6 routing remain manual checks.
- Fixes included: a remote Hysteria2/TUIC (UDP-only) relay now continues to the protocol-handshake and real-exit layers of `rout test ID` when the QUIC probe answered or was inconclusive (obfuscation and filtering look the same as silence); only a definite failure such as ICMP port unreachable stops the run. The 10-minute limit on reusing a stale DNS answer now counts from when the answer was really fetched, not from the cache timestamp that every stale refresh rewrote, so a relay no longer keeps forwarding to an obsolete address through a long DNS outage. Both were found in review before release and have regression tests that fail without the fix.
- Upgrading: no migration and no restart; see [Upgrading](docs/UPGRADING.md). Rollback caveat: an older Rout cannot read Remote server exits (`protocol: node`), so remove them or restore the automatic pre-upgrade backup before downgrading; native relays then run as GOST relays on their saved listening address and lose IPv6-only, dual-stack and outbound-policy behavior.
- **Verification status.** Automated: Go unit, race and vet checks, engine integration tests, systemd/OpenRC lifecycle, kernel accounting and the `verify` workflow passed on GitHub-hosted Ubuntu runners. That runner has IPv6 loopback, so the `::1` socket tests (dual-stack listeners and relays, IPv6-only node refusing IPv4 clients, IPv4/IPv6 kernel counters) ran and passed there rather than being skipped; this is loopback only. Opt-in real-network tests (`ROUT_TEST_REALNET=1`) are skipped in CI. **Not done:** acceptance on real VPS/NAT hosts — provider NAT and firewalls, public IPv6 routing, a real remote-server exit across the Internet, and Hysteria2/TUIC over a real UDP-restricted NAT. Simulated, injected-DNS and loopback tests are not a substitute for those; treat IPv6, outbound-policy and Remote server exit behavior on real hosts as unverified until you have checked it.
